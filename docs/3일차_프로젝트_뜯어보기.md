# 3일차 프로젝트 뜯어보기

## 1. `app/core/` 디렉터리

`app/core/`는 프로젝트 전반에서 공통으로 사용하는 핵심 설정을 관리하는 디렉터리이다.

현재 프로젝트에서는 데이터베이스 접속에 필요한 환경 설정과 SQLAlchemy 데이터베이스 연결 설정 등을 관리한다.

주요 파일은 다음과 같다.

- `config.py`: 데이터베이스 접속에 필요한 설정값을 관리한다.
- `db/databases.py`: 데이터베이스 연결 환경을 구성한다.
- `db/models.py`: 여러 데이터베이스 모델에서 공통으로 사용할 수 있는 Mixin 클래스를 정의한다.

### `app/core/config.py`

`config.py`는 프로젝트에서 사용할 환경 설정값을 관리하는 파일이다.

현재 프로젝트에서는 `pydantic_settings`의 `BaseSettings`를 상속한 `Settings` 클래스를 사용하고 있으며 다음과 같은 데이터베이스 설정을 관리한다.

- `DB_USER`: 데이터베이스 사용자
- `DB_PASSWORD`: 데이터베이스 비밀번호
- `DB_HOST`: 데이터베이스가 실행되는 호스트
- `DB_PORT`: 데이터베이스에 접근하기 위한 포트
- `DB_NAME`: 사용할 데이터베이스 이름

`model_config`의 `env_file`을 `.env`로 설정하여 `.env` 파일에 작성된 환경변수를 읽어 설정값으로 사용할 수 있도록 구성되어 있다.

마지막으로 `settings = Settings()`를 통해 설정 객체를 생성하며, 다른 파일에서는 `settings.DB_HOST`와 같은 방식으로 필요한 설정값에 접근할 수 있다.

### `app/core/db/databases.py`

`databases.py`는 `config.py`에서 관리하는 데이터베이스 설정값을 이용하여 SQLAlchemy의 데이터베이스 연결 환경을 구성하는 파일이다.

`DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT`, `DB_NAME`을 조합하여 `DATABASE_URL`을 생성한다.

현재 프로젝트에서는 MySQL을 사용하며 `asyncmy` 드라이버를 이용하여 비동기 방식으로 데이터베이스와 통신하도록 설정되어 있다.

`create_async_engine()`을 이용하여 비동기 SQLAlchemy Engine을 생성하고, `async_sessionmaker()`를 이용하여 데이터베이스 작업에 사용할 비동기 Session을 생성할 수 있도록 한다.

또한 `declarative_base()`를 통해 SQLAlchemy 모델들이 사용할 `Base`를 생성한다.

`async_get_db()` 함수는 필요한 곳에서 데이터베이스 Session을 사용할 수 있도록 제공한다.

데이터베이스 연결 흐름은 다음과 같다.

```text
.env
  ↓
config.py
  ↓
settings
  ↓
DATABASE_URL
  ↓
SQLAlchemy Engine
  ↓
Session
  ↓
MySQL Database

app/core/db/models.py

app/core/db/models.py에는 여러 데이터베이스 모델에서 공통으로 사용할 수 있는 Mixin 클래스가 정의되어 있다.

UUIDMixin: 각 데이터의 고유 식별자인 UUID를 관리한다.
TimestampMixin: 생성 시각(created_at)과 수정 시각(updated_at)을 관리한다.
SoftDeleteMixin: 데이터를 바로 완전히 삭제하지 않고 삭제 여부(is_deleted)와 삭제 시각(deleted_at)을 관리한다.

공통 기능을 Mixin으로 분리하면 여러 모델에서 같은 필드를 반복해서 작성하지 않고 재사용할 수 있다.

2. app/models/ 디렉터리

app/models/는 SQLAlchemy ORM을 이용하여 실제 데이터베이스 테이블에 대응하는 모델을 작성하는 디렉터리이다.

예를 들어 사용자 기능을 구현한다면 사용자 이름, 이메일, 나이 등의 컬럼을 가지는 User 모델을 작성할 수 있다.

현재 프로젝트 템플릿의 app/models/에는 __init__.py만 존재하며 실제 서비스에서 사용할 개별 모델은 아직 작성되어 있지 않다.

app/core/db/models.py가 여러 모델에서 사용할 공통 기능을 정의하는 곳이라면, app/models/는 실제 서비스에서 사용할 개별 데이터베이스 모델을 작성하는 곳이다.

3. app/repositories/ 디렉터리

app/repositories/는 데이터베이스에 접근하는 로직을 작성하는 디렉터리이다.

대표적으로 CRUD 작업을 담당할 수 있다.

Create: 데이터 생성
Read: 데이터 조회
Update: 데이터 수정
Delete: 데이터 삭제

Repository는 Service에서 필요한 데이터를 데이터베이스에서 조회하거나 저장·수정·삭제하는 역할을 담당한다.

현재 프로젝트 템플릿에는 __init__.py만 존재하며 실제 Repository 구현 파일은 아직 작성되어 있지 않다.

4. app/schemas/ 디렉터리

app/schemas/는 API 요청과 응답에서 사용할 데이터의 형태를 정의하는 디렉터리이다.

FastAPI에서는 주로 Pydantic 모델을 이용하여 요청 데이터의 자료형, 필수 값, 길이 등의 조건을 검증한다.

현재 프로젝트 템플릿에는 __init__.py만 존재하며 실제 Schema 파일은 아직 작성되어 있지 않다.

현재 practice_apis.py에서는 UserCreate, UserUpdate가 이러한 Schema 역할을 API 파일 안에서 함께 수행하고 있다.

향후 역할별로 코드를 분리한다면 이러한 Pydantic 모델을 app/schemas/에 작성할 수 있다.

5. app/services/ 디렉터리

app/services/는 애플리케이션의 비즈니스 로직을 담당하는 디렉터리이다.

비즈니스 로직은 서비스가 어떤 규칙에 따라 동작해야 하는지를 판단하고 처리하는 코드이다.

예를 들어 회원가입 시 이미 사용 중인 이메일인지 확인하고, 중복된 이메일이라면 회원가입을 거절하는 등의 규칙이 이에 해당한다.

현재 프로젝트 템플릿에는 __init__.py만 존재하며 실제 Service 구현 파일은 아직 작성되어 있지 않다.

현재 practice_apis.py에서는 이메일 중복 검사 등의 일부 비즈니스 로직이 API 코드 안에 함께 구현되어 있다.

6. app/apis/ 디렉터리

app/apis/는 클라이언트의 HTTP 요청을 받는 API 엔드포인트를 정의하는 디렉터리이다.

API 계층에서는 클라이언트의 요청을 받아 필요한 로직을 실행하고 그 결과를 응답으로 반환한다.

현재 프로젝트에는 practice_apis.py가 존재하며 회원 정보의 조회, 생성, 수정, 삭제를 연습하기 위한 API가 구현되어 있다.

app/apis/practice_apis.py

practice_apis.py에서는 APIRouter를 이용하여 /practice_api 경로를 기준으로 API를 묶어서 관리한다.

구현된 주요 API는 다음과 같다.

GET /users: 전체 회원 조회
GET /users/{user_id}: 특정 회원 조회
POST /users: 회원 생성
PATCH /users/{user_id}: 회원 정보 수정
DELETE /users/{user_id}: 특정 회원 삭제

또한 UserCreate, UserUpdate와 같은 Pydantic 모델을 이용하여 요청 데이터의 형식을 검증하고 있으며, 이메일 형식과 비밀번호 규칙을 검사하는 검증 함수도 포함되어 있다.

현재는 연습용 코드이기 때문에 API 파일 안에 요청 Schema와 일부 비즈니스 로직이 함께 작성되어 있다.

프로젝트 구조를 역할별로 분리한다면 요청 데이터 검증은 schemas/, 비즈니스 로직은 services/, 데이터베이스 접근 로직은 repositories/로 분리할 수 있다.

7. app/main.py

app/main.py는 FastAPI 애플리케이션을 생성하고 프로젝트의 여러 구성 요소를 연결하는 중심 파일이다.

FastAPI 애플리케이션 생성

app = FastAPI()를 통해 FastAPI 애플리케이션 객체를 생성한다.

API Router 등록

app.include_router(practice_apis.router)를 통해 practice_apis.py에서 만든 Router를 FastAPI 애플리케이션에 등록한다.

이를 통해 /practice_api로 시작하는 API들을 실제 애플리케이션에서 사용할 수 있다.

정적 파일 및 미디어 파일 설정

static, media 디렉터리가 존재하지 않을 경우 생성하도록 설정되어 있다.

app.mount()를 이용하여 다음 경로를 연결한다.

/static: CSS, JavaScript 등의 정적 파일 제공
/media: 사용자 업로드 파일 제공
Health Check API

/healthcheck는 서버가 정상적으로 동작하고 있는지 확인하기 위한 API이다.

정상적으로 동작하면 다음과 같이 응답한다.

{
  "status": "ok"
}
메인 페이지

/ 경로로 요청이 들어오면 static/index.html 파일을 반환한다.

또한 catch_all()을 통해 API나 정적 파일 경로가 아닌 다른 경로에 대해서 필요한 경우 index.html을 반환하도록 구성되어 있다.

8. pyproject.toml

pyproject.toml은 Python 프로젝트의 기본 정보와 프로젝트 실행에 필요한 의존성(라이브러리)을 관리하는 설정 파일이다.

현재 프로젝트는 Python 3.13 이상을 사용하도록 설정되어 있다.

주요 의존성은 다음과 같다.

fastapi: 웹 API 구현
sqlalchemy: 데이터베이스 ORM 및 데이터 접근
asyncmy: MySQL 비동기 연결
alembic: 데이터베이스 마이그레이션 관리
pydantic-settings: 환경 설정 관리
uuid6: UUID 생성
cryptography: 암호화 관련 기능 지원
9. uv.lock

uv.lock은 프로젝트에서 사용하는 패키지와 관련 의존성의 구체적인 버전을 고정하여 개발 환경을 일관되게 유지하는 파일이다.

pyproject.toml에서 프로젝트에 필요한 라이브러리와 버전 조건을 선언하면, uv.lock은 실제 설치되는 구체적인 의존성 버전 조합을 기록한다.

이를 통해 다른 개발 환경에서도 동일한 패키지 구성을 재현하는 데 도움을 준다.

10. 데이터베이스 연결 설정

현재 프로젝트의 데이터베이스 연결 과정은 다음과 같다.

.env 파일에 데이터베이스 접속 정보를 작성한다.
app/core/config.py의 Settings가 환경변수를 읽는다.
app/core/db/databases.py에서 설정값을 이용하여 DATABASE_URL을 만든다.
create_async_engine()을 이용하여 SQLAlchemy Engine을 생성한다.
async_sessionmaker()를 이용하여 데이터베이스 작업용 Session을 생성할 수 있도록 한다.
필요한 코드에서 Session을 이용하여 데이터베이스 작업을 수행한다.

현재 설정에서는 MySQL과 asyncmy를 사용하여 비동기 방식으로 데이터베이스와 통신한다.

11. SQLAlchemy 모델 작성과 Alembic 마이그레이션
SQLAlchemy 모델 작성

SQLAlchemy ORM 모델은 Python 클래스를 이용하여 데이터베이스 테이블의 구조를 표현한다.

실제 서비스의 모델은 app/models/에 작성하고, 필요한 경우 UUIDMixin, TimestampMixin, SoftDeleteMixin 등의 공통 기능을 재사용할 수 있다.

모델에서 테이블 이름과 컬럼 등을 정의하면 Python 코드에서 데이터베이스의 데이터를 객체 형태로 다룰 수 있다.

Alembic 설정

현재 alembic/env.py에서는 프로젝트의 Base와 DATABASE_URL을 가져와 Alembic과 SQLAlchemy 모델을 연결하고 있다.

target_metadata = Base.metadata를 통해 Alembic이 SQLAlchemy 모델의 메타데이터를 참고할 수 있도록 설정한다.

또한 프로젝트의 DATABASE_URL을 Alembic의 데이터베이스 연결 주소로 사용한다.

마이그레이션 수행 흐름

SQLAlchemy 모델의 구조를 변경한 뒤 다음과 같은 흐름으로 데이터베이스 구조에 반영할 수 있다.

SQLAlchemy Model 수정
        ↓
Migration 파일 생성
        ↓
Migration 내용 확인
        ↓
Database에 적용

Migration 파일을 자동 생성할 때는 다음과 같은 명령어를 사용할 수 있다.

alembic revision --autogenerate -m "migration message"

생성된 Migration 파일은 alembic/versions/에 저장된다.

Migration을 실제 데이터베이스에 적용할 때는 다음 명령어를 사용할 수 있다.

alembic upgrade head

즉 Alembic은 SQLAlchemy 모델의 변경 사항을 데이터베이스 구조에 반영하고, 그 변경 이력을 관리하기 위한 도구이다.

12. API 구현 흐름

프로젝트의 계층을 역할별로 분리하여 구현할 경우 전체적인 흐름은 다음과 같이 정리할 수 있다.

Client
  ↓
API
  ↓
Schema
  ↓
Service
  ↓
Repository
  ↓
Database

각 계층의 역할은 다음과 같다.

API: 클라이언트의 HTTP 요청을 받고 응답을 반환한다.
Schema: 요청 및 응답 데이터의 형태를 정의하고 검증한다.
Service: 서비스의 비즈니스 로직을 처리한다.
Repository: 데이터베이스의 데이터를 조회, 생성, 수정, 삭제한다.
Model: 데이터베이스 테이블의 구조를 정의한다.
Database: 실제 데이터를 저장한다.

현재 practice_apis.py는 연습용 API이기 때문에 Schema와 일부 비즈니스 로직이 하나의 API 파일에 함께 작성되어 있다. 이후 프로젝트가 확장되면 각 역할에 맞는 디렉터리로 코드를 분리하여 관리할 수 있다.
