# [Day 2] AI Worker 역할 및 작업 처리, 결과 저장 흐름

## 1. AI Worker와 Consumer 개념
- 무엇인가?
  * AI Worker: 무거운 딥러닝/머신러닝 모델의 추론(Inference) 작업을 웹 서버 외부에서 독립적으로 처리하는 백그라운드 프로세스.
  * Consumer: 이벤트 주도 아키텍처(EDA)나 메시지 큐 시스템에서 생산자(FastAPI)가 큐에 넣은 작업 메시지를 가져와서(consume) 처리하는 수신 주체. 본 프로젝트에서는 AI Worker가 Consumer 역할을 담당함.

- 왜 필요한가?
  * X-ray 사진을 분석해 폐렴을 예측하는 AI 연산은 CPU/GPU와 메모리를 많이 쓰고 수 초 이상의 시간이 소요됨.
  * 웹 서버가 이 작업을 직접 처리하면 서버 리소스가 부족해져 다른 사용자의 단순 조회 요청조차 응답하지 못하고 멈추게 됨.

- 우리 프로젝트에서는 어디에 쓰는가?
  * 의료진이 업로드한 X-ray 이미지 파일을 받아 폐렴 여부를 예측 분석할 때 사용함.


## 2. FastAPI와 AI Worker를 분리하는 이유
- 무엇인가?
  * 사용자 요청을 받고 응답하는 웹 서버(FastAPI)와 무거운 연산을 전담하는 백그라운드 일꾼(AI Worker)의 역할을 물리적/논리적으로 분리하는 구조임.

- 왜 필요한가?
  1) 서버 멈춤(이벤트 루프 블로킹) 방지: FastAPI는 비동기 방식으로 빠르게 요청을 처리하는데, 무거운 연산이 끼어들면 서버 전체 응답이 지연됨.
  2) 독립적인 수평 확장: 웹 접속자가 많아지면 가벼운 FastAPI 서버만 늘리고, AI 분석 요청이 밀리면 고성능 AI Worker만 따로 늘려 리소스와 비용을 절감할 수 있음.
  3) 장애 격리: AI 모델 분석 도중 메모리 부족(OOM)으로 꺼지더라도 Worker만 재시작될 뿐, FastAPI 웹 사이트는 중단 없이 정상 운영됨.

- 우리 프로젝트에서는 어디에 쓰는가?
  * FastAPI는 X-ray 이미지 업로드 접수 및 진행 상태 조회만 전담하고, 실제 폐렴 분석 연산은 AI Worker가 전담함.


## 3. 작업 처리 및 결과 저장 흐름
- 전체 흐름도:
  [의료진 브라우저] -> [FastAPI (요청 접수)] -> [Redis Queue (대기열)] -> [AI Worker (분석 처리)] -> [MySQL (결과 저장)]

- 상세 단계:
  1단계 (요청 접수): 의료진이 웹 화면에서 X-ray 이미지를 올리고 분석을 요청합니다.
  2단계 (대기열 등록 및 응답): FastAPI가 작업 고유 번호(Task ID)를 발급하고 Redis 큐에 작업을 넣은 뒤, 의료진에게 접수 완료 응답(Task ID)을 즉시 돌려줍니다.
  3단계 (작업 가져오기): AI Worker가 Redis 큐를 계속 확인하다가 새로 들어온 작업을 하나씩 꺼내옵니다.
  4단계 (AI 모델 분석): AI Worker가 이미지를 읽어서 폐렴 여부(양성/음성)와 신뢰도를 예측합니다.
  5단계 (결과 저장): AI Worker가 최종 분석 결과와 완료 상태를 MySQL 데이터베이스에 저장합니다. 이후 의료진은 Task ID로 완료된 결과를 확인합니다.
